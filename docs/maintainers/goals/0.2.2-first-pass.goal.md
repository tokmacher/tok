## Product Aim

Take Tok from 0.2.1 to a first useful 0.2.2 pass by improving confidence in the
supported bridge-first workflow.

The 0.2.2 theme is credibility density:

- make the live bridge state easier to understand
- make fallback and baseline behavior harder to miss
- make savings claims clearly tied to measured data
- add one reproducible proof loop or diagnostic path, but keep it guarded if it is not
  ready for the defended public surface

## Preferred Implementation Scope

Choose a focused slice that can land cleanly in one branch. Prefer this order:

1. Improve `tok doctor`, `tok bridge status`, or `tok stats` output so a user can
   quickly tell whether Tok is active, degraded, baseline-only, or not connected.
1. Add or tighten JSON fields and tests that expose the same verdicts for agents.
1. Add a small reproducible bridge proof loop only if it can be local, deterministic,
   and honest about whether savings were measured. If this becomes a CLI command, keep
   it hidden or under an existing experimental group unless the release surface is
   intentionally updated with tests.
1. Update docs only for behavior that actually changed.

Do not add speculative protocol features. Do not add remote resolver behavior. Do not
claim Tok Capability, Tok Session, stable SDK support, or protocol compliance.

## Concrete Acceptance Criteria

The first pass should leave the repo in this state:

- A user-visible or agent-visible bridge health verdict is clearer than in 0.2.1.
- Degraded, fallback, and baseline-only states are represented plainly.
- Savings are described as measured only when live stats prove they were measured.
- Any new command or output is tested.
- Public docs match the actual behavior.
- `src/tok/release_surface.py` still protects the defended 0.2.x surface. If you
  intentionally expose a new visible root command, update the release-surface tests and
  explain why it belongs in 0.2.x.
